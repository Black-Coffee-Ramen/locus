# Indoor Localization and Navigation System: Debugging and Optimization Report

This document outlines the core algorithmic, data structural, and machine learning challenges encountered during the final development phase of the Indoor Localization system, along with their respective engineering solutions.

## 1. Machine Learning Feature Density Mismatch (The "Teleportation" Glitch)
**Issue:** 
During field testing, the localization model exhibited severe instability in the A-wing. For example, a user standing at A-408 (x = -26) would occasionally be predicted as standing at A-419 (x = -3)—a 23-meter localization error. Interestingly, the B-wing was highly stable and accurate.

**Root Cause Analysis:** 
A diagnostic script was written to analyze the AP (Access Point) density in the `coordinates.json` training dataset. The analysis revealed a critical data collection asymmetry:
* **B-wing training data** recorded an average of **12-16 APs** per physical coordinate.
* **A-wing training data** only recorded an average of **8-9 APs** per coordinate.

During a live test, the Android device was capable of detecting over **50+ APs** in a single scan. The K-Nearest Neighbors (KNN) model computes distance by comparing the live scan's RSSI vector against the training vectors. Because the A-wing training data only contained 8 features, the KNN algorithm interpreted the remaining 42 live APs as "missing data" in the training point (assigning them a heavy distance penalty of -100 dBm). The model subsequently rejected the correct physical location and erroneously matched the user to distant coordinates that randomly shared identical weak background noise.

**Solution: Dynamic RSSI Truncation Filter**
We implemented a dynamic filtering mechanism in the backend (`app.py`). Before passing the live Wi-Fi fingerprint to the model, the server now truncates the payload to retain only the **Top 12 Strongest APs**:
```python
sorted_bssids = sorted(rssi_dict.items(), key=lambda x: x[1], reverse=True)
top_rssi_dict = dict(sorted_bssids[:12])
```
This restricts the live scan feature density to match the average density of the training dataset. By discarding the weak, fluctuating background noise, the teleportation issue in the A-wing was completely eliminated without compromising B-wing accuracy.

## 2. A* Pathfinding Graph Disconnects (HTTP 404 Navigation Errors)
**Issue:**
When users attempted to request a navigation route across the main junction (e.g., moving between the A and B wings, or from the Lift), the backend occasionally threw an HTTP 404 error, failing to calculate a route.

**Root Cause Analysis:**
The A* pathfinding algorithm relies on an interconnected graph of `walkable_nodes`. This graph was algorithmically generated by reading the surveyed `(x, y)` coordinates from the dataset. However, due to the manual nature of the survey, there were localized gaps in the physical data collection where no coordinates were captured (specifically at `x=27`, `x=31`, and the vertical lift connection at `y=2`). These gaps physically severed the graph, rendering nodes on the opposite side unreachable.

**Solution: Heuristic Graph Bridging**
The map generation script (`build_floor_map.py`) was updated to include an automated gap-filling heuristic. It now programmatically inspects the corridor logic (at `y=8`) and automatically injects bridging nodes into the `walkable_nodes` array to ensure graph continuity across both wings.

## 3. Zone-Based Arrival Detection (Off-Axis Coordinate Shift)
**Issue:**
The backend was failing to trigger "Arrival" proximity events accurately for specific room types. For example, a user standing exactly in front of a Faculty Room door would be registered as being 2 meters away, preventing the navigation system from completing the route.

**Root Cause Analysis:**
To visually separate the rooms on the map UI and reflect real-world parallelism, Faculty rooms and Labs were assigned distinct artificial Y-coordinates (e.g., Faculty rooms at `y=10`, Labs at `y=5`, while the main corridor was at `y=8`). 
The `nearest_room_to_pos()` function in `navigation.py` utilized standard Euclidean distance. Because the user's predicted position was always snapped to the corridor (`y=8`), the Euclidean calculation artificially inflated the distance to the rooms by factoring in the artificial UI Y-offsets.

**Solution: Axis-Specific Distance Calculation**
We rewrote the arrival detection logic. If a room is not physically located on the central corridor axis (`coord[1] != corridor_y`), the algorithm discards the Y-axis and relies exclusively on absolute X-axis deviation:
```python
if coord[1] != corridor_y:
    dist = abs(coord[0] - pos[0])
else:
    dist = math.hypot(coord[0] - pos[0], coord[1] - pos[1])
```
This aligns the mathematical distance calculation with physical reality, restoring perfect arrival detection.

## 4. Room Layout Interleaving Discrepancies
**Issue:**
The spatial mapping of specific discussion areas and laboratories did not reflect physical reality. For instance, the Discussion Area (A-417) was incorrectly mapped to the far end of the corridor, while it physically sits sandwiched between two distinct lab clusters.

**Root Cause Analysis:**
A transcription error during the initial mapping phase resulted in the `representative_x` coordinates for certain nodes (A-414/A-417 and B-414/B-417) being swapped. This corrupted both the UI display order and the A* path destination.

**Solution: Map Registration Overhaul**
The `room_mapping.json` matrix was completely restructured to ensure alternating spatial interleaving:
`Meeting Room -> Lab -> Lab -> Discussion Room -> Lab -> Lab -> Discussion Room -> Lab`
This ensures that the final destination node passed to the A* pathfinder exactly matches the physical doorway the user intends to walk to.
